# Assumptions register — UC-08 Learning Streaks & Milestones

Every field name, response shape, enum value, threshold and behaviour in this
component that the company has **not** specified is listed here. Each row says
what we assumed, why, what breaks if the assumption is wrong, and where the
assumption lives in the code.

Anything **not** in this table is taken from the platform contract in the scope
document: the `session_id` handling, the NARIC enum and its `naric_level_source`
values, the explanation-profile bands, the integer 0–100 course-progress type,
the source-status vocabulary, the lowercase serialisation rule, the streak record
shape, the badge record shape, the port list and method names, the config
variable names, and the seven API routes.

Read `docs/SHARED_CONTRACT.md` alongside this: it marks every emitted field
**specified** or **assumed**, and the assumed ones point back to these IDs.

| ID | Area | Assumption | Why | Risk if wrong | Where in code |
|---|---|---|---|---|---|
| A-01 | Streak window | "An interaction in the last 24 hours" is a **rolling window** `[now - STREAK_WINDOW_HOURS, now)`, evaluated at the moment of each interaction — not a comparison of calendar days. | The scope says "the last 24 hours … from the current UTC time", and explicitly warns that *the last 24 hours* and *yesterday* are different rules. | If the company means calendar "yesterday", activity 25 hours ago that still falls on the previous calendar day would keep a streak we reset. Learner-visible and unrecoverable. | `uc08/domain/streak_rules.py::decide`, `window_start_for` |
| A-02 | Once per day | The streak increments only when (a) a prior qualifying interaction fell in the window **and** (b) no increment has yet occurred for the current **UTC calendar day**. Condition (b) is derived from `last_activity_at` falling on the same UTC day as `now`. | The scope says the streak increments by one *day*, and asks for the rule to be defined precisely. Deriving (b) from the record we own avoids a second store. | A learner active at 23:50 and again at 00:10 UTC gets +1, because those are two UTC days. If the company means "a day" in the learner's local time, boundaries shift by up to 14 hours. | `uc08/domain/streak_rules.py::decide` (step 2), `apply_same_day` |
| A-03 | Boundary inclusivity | Exactly 24h 00m 00s qualifies: the test is `now - prior <= window`. | The specified pair is 23h59m and 24h01m; the exact instant is unspecified, and inclusivity favours the learner. | One second of difference for one interaction in a rare case. Lowest-consequence row here. | `uc08/domain/streak_rules.py::decide`, `tests/unit/test_streak_boundary.py::test_exactly_24h_ago_is_inside_the_window` |
| A-04 | Continuity source | Continuity is decided from the `ActivityProvider`. The persisted streak record is a **fallback only** when that read fails, and a failed read can never produce a reset — it yields `unchanged_source_degraded`. | The scope frames the check as a read of activity, and the mock matrix drives the boundary through the activity provider. An outage is a system problem, so the learner must not pay for it. | If the company expects a reset when activity cannot be read, streaks would live longer than intended. We chose the direction that cannot destroy a streak. | `uc08/application/streak_service.py::_read_continuity`, `_next_record` |
| A-05 | Idempotency | Idempotency is keyed on a caller-supplied opaque `interaction_id`, stored in an added `ProcessedInteractionStore` port. Marking happens **only after the streak write commits**. | The scope requires "replaying the same interaction must not change the result" but names no key and no store. Marking after the commit keeps a failed write replayable. | If the company has its own interaction identity with different uniqueness, replays could be missed (double-count, absorbed by A-02) or over-suppressed. | `uc08/ports/repositories.py::ProcessedInteractionStore`, `uc08/application/streak_service.py::record_activity` |
| A-06 | Explanation profiles | `LEVEL_4 → basic` and `LEVEL_6 → intermediate`. | The scope gives the bands and states that levels 4 and 6 are an assumption to record. | Explanations pitched one band off for two of six levels. Cosmetic here — UC-08 only carries the profile for a caller. | `uc08/domain/enums.py::EXPLANATION_PROFILE_BY_LEVEL`, `uc08/domain/naric.py::explanation_profile_for` |
| A-07 | Interaction identity | `interaction_id` is opaque, supplied by the caller, and unique per coaching interaction per account. UC-08 does not generate or parse it. | Nothing about interaction identity is specified, and inventing a format would bind the platform to ours. | If ids are reused across accounts, nothing breaks (the store is keyed on `(user_id, interaction_id)`). If they are reused *within* an account, a genuine interaction is treated as a replay. | `uc08/api/schemas.py::RecordActivityRequest` |
| A-08 | Course progress | Completion is accepted as an integer 0–100, or a numeric/percentage string (`"72"`, `"72%"`, `"72.4 %"`, truncated). A fractional `0 < x < 1` representation is reported **`invalid`**, never multiplied by 100. | The contract fixes the type as an integer 0–100. `0.5` could mean 50% or half a percent, and this component never guesses. | A provider that legitimately sends fractions would report `invalid` for every learner until its adapter converts. Visible in logs and in `course_progress_status` — loud, not silent. | `uc08/domain/naric.py::normalise_completion_percent` |
| A-09 | Window contents | The interaction being recorded is excluded from the window count, matched by `interaction_id` **and** by `occurred_at < now`. | An activity read model that already shows the current interaction would otherwise make every interaction look like continuous activity, so a learner returning after a month would never reset. | If a provider back-dates the current interaction and reuses no id, it could be counted as prior activity and a reset would be missed. | `uc08/application/streak_service.py::_read_continuity` |
| A-10 | Freeze offer store | The freeze offer is a first-class record (`FreezeOffer`) in an added `FreezeOfferRepository` port, with statuses `offered`, `accepted`, `declined`, `expired`. | The scope requires the offer to be modelled explicitly — offered, accepted, declined, expiring — and that state has to live somewhere. The specified port list has no home for it. | None to the platform: this record is internal and is not part of the published contract unless the company wants it. | `uc08/domain/models.py::FreezeOffer`, `uc08/ports/repositories.py::FreezeOfferRepository` |
| A-11 | Freeze calendar | "Once per calendar month" means the **UTC** calendar month, compared on `YYYY-MM`. `FREEZE_PER_CALENDAR_MONTH` must be `1`; any other value fails at startup. | The scope requires the calendar to be named. The platform streak record carries a single `freeze_used_at`, so more than one use per month is not representable without changing a fixed shape. | Learners in UTC+13 could see a freeze allowance reset up to 13 hours before their local month turns. A larger allowance is a contract conversation, and the config refuses it loudly rather than mis-counting. | `uc08/domain/time_utils.py::utc_month_key`, `uc08/domain/streak_rules.py::freeze_available_at`, `uc08/config.py::_freeze_allowance_is_representable` |
| A-12 | Offer expiry | An unanswered freeze offer expires **24 hours** after it is made (`FREEZE_OFFER_EXPIRY_HOURS`), evaluated lazily on the next read or interaction. | The scope requires an expiry to be defined and recorded. 24 hours matches the 24-hour freeze the offer grants. | An offer window that is too short frustrates a learner who was away; too long and a stale offer resurrects an old streak. Configurable, so it is one env value to change. | `uc08/config.py`, `uc08/application/streak_service.py::_open_offer` |
| A-13 | Allowance accounting | Only an **accepted** freeze consumes the monthly allowance. A declined or expired offer consumes nothing. | The scope says a freeze is "usable once per calendar month"; usable is about use. | If the company means an offer consumes the allowance, learners would get fewer freezes than we grant. Generous direction, and visible in `freeze_used_at`. | `uc08/domain/streak_rules.py::freeze_available_at`, `uc08/application/streak_service.py::accept_freeze` |
| A-14 | Week identity | A week is identified by its ISO-8601 week key in UTC, `GGGG-Www` (e.g. `2026-W11`), and `week_start_at` is 00:00:00Z on that Monday. | The scope names Monday as the summary day and gives no week identifier. ISO weeks make Monday the first day by definition and sort lexically. | If the company keys weeks differently (a date, a Sunday-start week), the `week` field needs mapping. Contained: it is one field with one derivation. | `uc08/domain/time_utils.py::iso_week_key`, `previous_iso_week_bounds` |
| A-15 | Summary listing | `WeeklySummaryRepository` gains `list_for_user(user_id)` beyond the specified `save`/`get`. | `GET /api/v1/weekly-summaries` is a specified endpoint and cannot be served by `get(user_id, week)` alone. | None to the platform: it is a read on a store we own. | `uc08/ports/repositories.py::WeeklySummaryRepository.list_for_user` |
| A-16 | Topic mentions | `topics_in_window` returns `TopicMention(name, first_mentioned_at)` rather than bare names. | The specified signature takes `since` and no `until`, and "topics covered **last week**" needs the window closed at the week end. The timestamp lets the caller close it without changing the signature. | A provider that cannot supply a first-mention timestamp would have to synthesise one. The alternative — adding `until` to a fixed signature, or accepting this-week leakage — is worse. | `uc08/domain/models.py::TopicMention`, `uc08/application/weekly_summary_service.py::_topics` |
| A-17 | Questions asked | "Questions asked" last week is the **count of coaching interactions** in that week. | The activity port reports interactions; the scope asks for questions. One interaction is treated as one question. | If an interaction can contain several questions, the summary undercounts. The badge thresholds use the provider's own `question_count`, so badges are unaffected. | `uc08/application/weekly_summary_service.py::_questions` |
| A-18 | Freeze mechanics | The streak resets immediately when the missed day is determined; the offer carries `preserved_streak_days`, and **accepting restores** `preserved + days active since the reset`. It is not held in limbo. | An unanswered offer must not preserve a streak indefinitely. Resetting first and restoring on acceptance makes the reported streak always something the learner has actually earned, and makes expiry a no-op rather than a compensating write. | Between the miss and the acceptance a learner sees the reset value, which may read as harsh. The alternative shows a streak that can be revoked. | `uc08/domain/streak_rules.py::apply_freeze_acceptance`, `uc08/application/streak_service.py::_build_offer_if_eligible` |
| A-19 | Summary retry cadence | A failed send sets `next_retry_at` to the **next UTC midnight**; the following day's generation call retries the delivery instead of generating a new record. Only the most recent summary is ever retried, so retries stop when a newer week is generated. | The scope says "retry the following day" and "never batch-send missed weeks". Bounding retries by "only the latest" avoids an arbitrary attempt cap. | A summary that fails all week is abandoned when the next week's is generated. That is the no-batch-send rule, chosen deliberately. | `uc08/application/weekly_summary_service.py::_attempt_send`, `_retry_latest_if_due` |
| A-20 | Skipped weeks | `skipped_weeks` lists ISO weeks between the last generated summary and the current one; empty when the account has no prior summary. Capped at 52 entries, with the true total stated in `omission_notes`. | The scope requires missed weeks not to be sent; naming them is how a caller can explain the gap. The cap keeps a multi-year gap from producing an unbounded list. | A very long absence reports the most recent 52 weeks plus a count. Truncation is stated on the record, not silent. | `uc08/application/weekly_summary_service.py::_skipped_weeks`, `MAX_LISTED_SKIPPED_WEEKS` |
| A-21 | Identifier formats | `badge_id` is `badge-<milestone>-<user_id>`; badge event id `evt-badge-<milestone>-<user_id>`; summary id `ws-<user_id>-<week>`; offer id `fo-<user_id>-<utc timestamp>Z`; incident id `inc-streak-write-<user_id>-<utc timestamp>Z`. All derived, none random. | No id formats are specified. Deriving them from the account plus the milestone makes a duplicate badge unrepresentable rather than merely guarded against, and keeps the whole component free of randomness. | If the platform needs opaque or globally unique ids, these are predictable and contain the account id. Changing the format is a one-function change. | `uc08/application/badge_service.py::badge_id_for`, `uc08/application/weekly_summary_service.py::_build`, `uc08/application/streak_service.py::_build_offer_if_eligible` |
| A-22 | Identity mechanism | In this build the account arrives in the `X-UC08-Subject` request header, read by one adapter. It is explicitly **not** production authentication. | No authentication is specified and none may be invented. What matters is the invariant: identity comes from the request context, never from a path, query or body field. | Deployed as-is, any caller could claim any account. The header adapter is the single replacement point, and `docs/INTEGRATION.md` covers the swap. | `uc08/adapters/identity/header.py`, `uc08/ports/identity.py` |
| A-23 | Adapter construction | Every upstream adapter is constructed as `(clock, *, timeout_seconds)` and exposes `timeout_seconds`. Adapter-specific configuration is read by the adapter from the environment. | The composition root must build any registered provider without knowing which it is; that is what makes registration one line. | An adapter needing constructor arguments must read them from the environment instead. Documented in the template. | `uc08/registry.py::build_provider`, `uc08/adapters/real/_template.py` |
| A-24 | Conformance harness | Upstream adapters expose `conformance_scenarios()` returning builders for `available`, `empty`, `unavailable`, `timeout`, `invalid`; declaring the scope-named scenarios additionally opts the adapter into the behavioural equivalence suite. | This is what makes "no new test needs writing to validate a real adapter" true rather than aspirational. | An adapter author must build a local stub of their upstream. That is the cost of the guarantee, and the template pre-writes the shape. | `uc08/ports/conformance.py`, `tests/conformance/` |
| A-25 | Write failure with no prior record | If both write attempts fail and the account had **no** previous record, the intended record is returned as the response view while nothing is persisted; `persistence_outcome` is `preserved_last_known` and the incident reports `preserved_streak_days=0`. | There is no "last known" count to preserve. The caller is told plainly that nothing committed. | A caller that ignores `persistence_outcome` could show a streak of 1 that is not stored. The field, the log line and the alert all say otherwise. | `uc08/application/streak_persistence.py::_preserve` |
| A-26 | Empty read model | `GET /api/v1/streaks` for an account with no record returns a zero-valued streak (`current_streak_days: 0`, null timestamps) rather than a 404. | A learner who has never interacted has a streak of zero, not a missing resource. Keeps the caller free of a special case. | A caller expecting 404 sees 200 with zeros. Stated in `docs/SHARED_CONTRACT.md`. | `uc08/application/streak_service.py::_empty_record` |
| A-27 | Where progress is carried | `course_progress_percent` and `course_progress_status` are carried on the gap report's `Topic`, because the gap report is the only upstream that reports progress to UC-08. | Course progress is in the platform contract but no port method returns it, and adding a fifth method to the fixed `ActivityProvider` shape would be a larger change. | If progress belongs to the learner rather than the suggestion, the field moves. It is one field on one record. | `uc08/domain/models.py::Topic` |
| A-28 | Freeze decline | `decline_freeze` exists as a service operation but has **no endpoint**: the specified API surface has exactly seven routes and none of them is a decline. | Inventing an eighth route would breach a fixed contract. Expiry means an unanswered offer resolves anyway. | A frontend cannot record an explicit decline until the route is agreed. Listed as an extension point in `docs/SHARED_CONTRACT.md`. | `uc08/application/streak_service.py::decline_freeze` |
| A-29 | Badge counting | `question_count` is a **lifetime total** for the account, and milestones are compared against it. A count that jumps awards every threshold crossed, ascending. | The scope says "total question count" and requires a 10→60 jump to award every milestone crossed. | If the count is periodic rather than lifetime, badges would be awarded repeatedly — prevented in practice by the badge store being idempotent on `(user_id, milestone)`. | `uc08/application/badge_service.py::evaluate` |
| A-30 | Local persistence | Two local backends, `memory` (default) and `jsonfile` under `PERSISTENCE_DIR`. Neither is a production database, and there is no ORM or company schema. | The scope forbids a production database and requires persistence behind an interface. | None: both are development conveniences behind `uc08/ports/repositories.py`. | `uc08/adapters/persistence/` |
| A-31 | Logging library | `structlog` is the platform default; where it is absent this build uses stdlib `logging` with a JSON formatter behind the same `get_logger` call. | The stack allows either. No module in `uc08/` depends on which is installed. | None. Swapping to `structlog` is one file. | `uc08/logging_setup.py` |

## Assumptions an integrator must verify before writing a real adapter

Ordered by what breaks worst if it is wrong.

1. **A-01, A-03** — that the qualifying window is a rolling 24 hours from the current UTC time, and inclusive at exactly 24h. Wrong here, streaks die.
2. **A-02** — that a "day" is a UTC calendar day. If the platform means learner-local days, the boundary moves and this needs a contract conversation, not a patch.
3. **A-09** — whether the real activity read model includes the interaction currently being recorded, and whether the id we are given matches the id it reports.
4. **A-04** — what the platform wants when the activity read model is down. We preserve; confirm that is intended.
5. **A-05, A-07** — that the caller's `interaction_id` is stable and unique per account, so replays are recognised.
6. **A-08, A-27** — the real representation and ownership of course progress.
7. **A-11, A-12, A-13** — the freeze calendar, the offer expiry and what consumes the allowance. All learner-visible.
8. **A-14, A-17** — the week key the platform expects, and whether one interaction is one question.
9. **A-22** — the real authentication mechanism, before this is deployed anywhere.
