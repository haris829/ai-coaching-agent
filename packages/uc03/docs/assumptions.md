# UC-03 — Assumptions register

Every field name, response shape, enum value, message and behaviour that UC-03
invented because the company has not specified it. If the platform disagrees
with any row, that row is the change — the surrounding code is built to absorb
it.

Status key: **ASSUMED** — we chose it. **SPECIFIED** — given by the company or
the platform contract, recorded here only where we previously diverged.

| ID | Area | Assumption | Why | Risk if wrong | Where in code |
|---|---|---|---|---|---|
| A-01 | Topic vocabulary | The controlled tag set is exactly these 17 lowercase values: `contract_formation`, `contract_remedies`, `negligence`, `criminal_liability`, `criminal_procedure`, `civil_procedure`, `land_and_property`, `employment`, `company_and_insolvency`, `family`, `immigration`, `wills_and_probate`, `evidence`, `human_rights`, `legal_system`, `professional_conduct`, `unclassified` | The brief required a controlled vocabulary for gap tracking but did not enumerate one. | A-07 | Depth grouping | Six qualification levels collapse to three depths: L3/L4 → FOUNDATION, L5/L6 → INTERMEDIATE, L7/L7_PLUS → ADVANCED | The contract specifies six levels; it does not say how many distinct explanation registers there should be. | Explanations pitched at the wrong register — e.g. if the company wants L7 and L7_PLUS treated differently, they currently are not. | `_NARIC_TO_DEPTH` in [uc03/explanation.py](../uc03/explanation.py) |

| A-09 | Framing strategy set | Six framings: `analogy`, `worked_example`, `contrast_near_miss`, `first_principles`, `procedural_walkthrough`, `misconception_correction` | The review named these as an example ("for example …"), not a fixed list. | Too few framings means exhaustion arrives sooner than the company expects; a different pedagogic taxonomy would need remapping of stored `framing` values. | `FramingStrategy` in [uc03/domain/enums.py](../uc03/domain/enums.py) |
| A-10 | Framing value casing | Lowercase `snake_case` | Consistency with the specified lowercase `unclassified` and `retrieved`/`default`. | Mismatch with a company framing vocabulary. | `FramingStrategy` |
| A-11 | Action → framing preference | Each follow-up action has a preference order over the framing pool (e.g. ANOTHER_EXAMPLE prefers `worked_example` first); all actions draw from the same pool and none may repeat | The requirement is "never repeat"; it does not say which framing each action should prefer. | A follow-up feels less apt than it could, but never repeats. | `_ACTION_PREFERENCE` in [uc03/explanation.py](../uc03/explanation.py) |
| A-12 | Paraphrase threshold | Content-word Jaccard overlap ≥ **0.60** counts as a repeat | "A paraphrase is a repeat" was specified; the measure was not. | Too low rejects legitimately distinct explanations (visible as `ERROR` + retry); too high lets reworded repeats through. | A-13 | Concept key | `"{topic_tag}|{sorted distinct words >3 chars}"` derived from the question subject | Framing state must be scoped "per concept"; concept identity was not defined. | Too coarse merges distinct concepts (framings exhaust early); too fine lets the same concept be re-explained with a repeated framing. | `concept_key` in [uc03/explanation.py](../uc03/explanation.py) |
| A-14 | Exhaustion behaviour | A dedicated `FRAMINGS_EXHAUSTED` status with `parts: null`, plus a message offering to go deeper or move on | "Say so honestly" was specified; the wire representation was not. | A consumer that only handles ANSWERED / ERROR will not recognise the status. | `ResponseStatus.FRAMINGS_EXHAUSTED`, `Settings.framings_exhausted_message` |
| A-15 | Paraphrase rejection surface | A rejected paraphrase returns `status: ERROR` with `retry_available: true`, and does **not** consume a framing | Rejection was specified; the surface was not. Chose ERROR because it is a generator fault, not a learner-visible dead end. | A consumer may show a scarier error than intended. | [uc03/service.py](../uc03/service.py) step 8 |
| A-16 | Follow-up endpoint shape | `POST /uc03/questions/{question_id}/follow-up` with body `{action, session_id}` | No route was specified. | Route churn at integration; the service method is independent of the route. | [uc03/api.py](../uc03/api.py) |
| A-17 | Context object shape | `LearnerContext` = `user_id`, `session_id`, `naric_level`, `naric_level_source`, `practice_area`, `practice_area_availability` | The brief listed the *data* UC-03 may need (NARIC level, practice area, session_id, user_id) but not the object. | The upstream context service returns a different shape; absorbed inside the adapter, not the core. | `LearnerContext` in [uc03/domain/models.py](../uc03/domain/models.py) |
| A-18 | Practice-area provenance | `practice_area_availability` uses `PROVIDED` / `MISSING` / `PROVIDER_UNAVAILABLE`, **not** the `retrieved`/`default` pair used for the level | Practice area has a genuine third state — the learner has no recorded speciality — that retrieved/default cannot express. | A-20 | Uppercase enums elsewhere | `status`, `classification` and `follow_up_actions` values stay UPPERCASE | Taken from the original brief's own JSON example. ## Open questions for the platform team

1. **A-20** — should `status`, `classification` and `follow_up_actions` be lowercase like `rating_state` and the topic tags? They currently follow the original brief's uppercase examples.
2. **A-01** — is there an existing company topic taxonomy this vocabulary should mirror?
3. **A-09** — is the framing set fixed, or should it be configurable per subject area?
4. **A-23** — is the company event log readable by `question_id`, or does the framing/follow-up state need its own store?
5. **A-07** — should `LEVEL_7` and `LEVEL_7_PLUS` receive materially different explanations?
