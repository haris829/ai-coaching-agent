# UC-05 — Assumptions register

Every invented field name, shape, enum value or behaviour that the company has
not specified appears here. Anything **not** in this register is either fixed by
the platform contract (section 3 of the brief) or is a direct restatement of a
requirement.

**How to use this before writing a real adapter:** the rows tagged
`Check before integrating` in the *Risk if wrong* column are the ones an
integration engineer must verify against the real upstream **before** writing
the adapter, not after. `docs/INTEGRATION.md` lists them again per dependency.

Status key: **INVENTED** — we made it up. **INFERRED** — the brief implies it
but does not state it. **DEFERRED** — we chose a placeholder because the
company owns the real answer.

## 1. The dialogue

| ID | Area | Assumption | Why | Risk if wrong | Where in code |
|---|---|---|---|---|---|
| A-EXCHANGE-DEF | Dialogue accounting | **INVENTED.** An *exchange* is one guiding question from the system plus the learner response to it. It is **opened** when the guiding question is emitted and **completed** when the learner replies. `exchanges_used` counts opened exchanges, so a learner who has been asked five guiding questions has used five of five, and the cap fires on their fifth reply. | The brief fixes the cap at five "per question" but never defines the unit. Counting on emission is the only definition under which the learner reliably receives exactly `cap` guiding questions; counting on reply would deliver `cap + 1`. | If the company counts a "system turn plus learner turn" only once *both* have happened, our cap fires one guiding question earlier than theirs. Learner-visible. **Check before integrating.** | `uc05/domain/models.py::ExchangeRecord`, `Dialogue.exchanges_used`, `state_machine.Transition.opens_exchange` |
| A-EXCHANGE-NUMBERING | Interaction log | **INVENTED.** An interaction record's `exchange_number` is the number of the exchange the response belongs to. Every guiding response opens exactly one exchange and writes exactly one record, so a dialogue with N exchanges has N question-bearing records numbered 1..N, plus at most one terminal record (offer / answer / capped answer) carrying the then-current number. | "One interaction record per exchange" needs a rule for records that do not open an exchange — the exit offer, the direct answer. | A consumer counting records to derive exchange usage would over-count by the number of terminal records. Fix is to filter by `response_kind`. | `uc05/application/socratic_service.py::_finalise` |
| A-SM-EVENTS | State machine | **INVENTED.** The eleven `DialogueEvent` names. | The brief requires every transition to be "triggered by an identified event" but names no events. | None externally — events are internal. They appear in logs, so a log consumer would need remapping. | `uc05/domain/enums.py::DialogueEvent` |
| A-OFFTOPIC-NO-COST | Exchange accounting | **INFERRED.** An off-topic message is redirected, re-poses the question already on the table, and does **not** consume an exchange. | An exchange is defined as reasoning about the question. Charging a learner an exchange for asking the time would burn their budget on nothing. | If the company intends every learner turn to cost an exchange, dialogues run longer here than there. | `state_machine.py::T03_redirect_off_topic` |
| A-IMPLICIT-DECLINE | Exit confirmation | **INVENTED.** A substantive response arriving while an exit offer is open is treated as an implicit decline: the dialogue resumes **and** the response is processed as a normal exchange. | The learner answered the question instead of the offer. Refusing the content or discarding it would both be worse than accepting it. | If the company would rather re-prompt for a yes/no, we accept reasoning they would reject. Learner-visible but benign. | `state_machine.py::T09_implicit_decline` |
| A-REASSERT | Exit confirmation | **INVENTED.** Repeating the direct-answer request while an offer is open counts as confirming it. | The learner has now asked twice. The rule that matters — never exit on the *first* request — is still honoured. | If the company requires a literal affirmative token, we exit one turn earlier than they would. | `state_machine.py::T08_exit_reasserted` |
| A-CLOSURE-KIND | Response kinds | **INFERRED.** When the learner reaches the conclusion themselves (`resolution = learner_reasoned`), the response kind recorded is `acknowledgement_and_guiding_question` and the reply is a neutral acknowledgement plus a fixed consolidating question. | The published `response_kind` vocabulary has exactly five members and none of them means "closure". Using `direct_answer` would violate section 5.8. We did not invent a sixth value. | A consumer segmenting by `response_kind` cannot distinguish a closing turn from an ordinary one; they must read `resolution`. **Raised as a contract gap — see §5 below.** | `state_machine.py::T04_learner_reasoned`, `vocabulary.py::CONSOLIDATING_QUESTION` |
| A-CONSOLIDATING-Q | Dialogue closure | **INVENTED.** The consolidating question is a fixed string, not generated. | The dialogue is closing; asking a generator for one more question is an opportunity for it to emit the answer. | Slightly less tailored than a generated question. | `vocabulary.py::CONSOLIDATING_QUESTION` |
| A-CONTEXT-ONCE | Learner context | **INVENTED.** Learner context is fetched once, when the dialogue opens, and reused for every exchange in it. | A dialogue is one question. Re-fetching could change the explanation profile between exchange three and four, and would make `naric_level` inconsistent across the interaction records of a single dialogue. | If the company expects a mid-dialogue level change to take effect immediately, it takes effect on the learner's next question instead. | `socratic_service.py::_context_from_dialogue` |

## 2. Vocabularies

| ID | Area | Assumption | Why | Risk if wrong | Where in code |
|---|---|---|---|---|---|
| A-ACK-SET | Acknowledgements | **INVENTED.** Six neutral acknowledgements, plus fixed strings for resume, redirect and closure. Selection is deterministic by exchange number. | The brief requires "a constrained acknowledgement set rather than trusting free generation". Deterministic selection makes the neutrality test exhaustive rather than sampled. | Tone mismatch with the company's voice. Cheap to change: one tuple, and the neutrality test re-runs against it. | `uc05/domain/vocabulary.py::ACKNOWLEDGEMENTS` |
| A-PRAISE-LIST | Acknowledgements | **INVENTED.** 38 prohibited praise terms, matched on word boundaries with apostrophes flattened. Applied to our own fixed strings **and** to every generator output. | "Good job", "excellent", "well done" and "exactly right" are named in the brief; the rest are the obvious neighbours. Word-boundary matching stops "great" firing inside "greater". | A praise term we did not list could reach a learner. Mitigated by the list being the single checkpoint — adding a term protects every path at once. **Check before integrating** if the company has a house style guide. | `vocabulary.py::PRAISE_TERMS`, `praise_terms_in` |
| A-FRUSTRATION-SET | Frustration detection | **INVENTED.** 28 explicit phrasings of being stuck. | The brief gives one example ("I genuinely have no idea") and rules out sentiment analysis. | A phrasing we did not list leaves the learner in the dialogue — the safe direction of failure, since the cap and the exit offer both still exist. **Check before integrating.** | `vocabulary.py::EXPLICIT_FRUSTRATION_PHRASES` |
| A-FRUSTRATION-RULE | Frustration detection | **INVENTED.** A phrase fires only when it forms a **whole clause** of the message *and* the message carries no substantive reasoning alongside it (no other clause with ≥ 3 content tokens). | Substring matching would rescue someone who wrote "I don't know *if* consideration applies here". The second condition stops "I'm stuck, but is it because consideration must move from the promisee?" from rescuing a learner who is visibly still reasoning — the brief's explicit concern. | Too strict: a genuinely stuck learner who adds a sentence is not rescued, and must use the cap or ask directly. Too loose: someone enjoying a hard problem is pulled out of it. We chose to err strict. | `uc05/domain/intent_rules.py` |
| A-CASUAL-SET | Frustration detection | **INVENTED.** 14 casual-difficulty phrasings, recognised as a **separate** intent that continues the dialogue. | The brief requires casual difficulty and explicit frustration to be separable outputs, not one folded into the other. | An unlisted casual phrasing falls through to `substantive_response`, which behaves identically. Low risk. | `vocabulary.py::CASUAL_DIFFICULTY_PHRASES` |
| A-REQUEST-SET | Direct-answer requests | **INVENTED.** 13 request phrasings, matched by containment rather than whole clause. | These are unambiguous, and an instruction-shaped message must still be *heard* as a request. | An unlisted phrasing is treated as a substantive response; the learner asks again or hits the cap. | `vocabulary.py::DIRECT_ANSWER_REQUEST_PHRASES` |
| A-CONFIRM-SET | Exit confirmation | **INVENTED.** Confirmation and decline phrase sets, whole-clause matched, decline checked first. | Needed to make the two-step exit operable. | An unrecognised "yeah go on" leaves the offer open; the learner repeats themselves (which A-REASSERT then confirms). | `vocabulary.py::EXIT_CONFIRMATION_PHRASES`, `EXIT_DECLINE_PHRASES` |
| A-OFFTOPIC-SET | Off topic | **INVENTED.** Six off-topic markers. | Needed to exercise the redirect path deterministically. | An unlisted aside is treated as a substantive response and costs an exchange. | `vocabulary.py::OFF_TOPIC_PHRASES` |
| A-CONCLUSION-SET | Learner conclusion | **INVENTED.** Six conclusion markers ("so the answer is", …). | The platform's `learner_reasoned` resolution otherwise has no reachable path. | Under-detection leaves the dialogue open to the cap. Over-detection closes a dialogue early. | `vocabulary.py::CONCLUSION_MARKERS` |
| A-INTENT-VOCAB | Intent | **INVENTED.** Two intents added to the six the brief fixes: `casual_difficulty` and `learner_reasoned_conclusion`. | The first because separability is required; the second because `learner_reasoned` is otherwise unreachable. | A company classifier returning only the six still works — the two extras simply never appear. Additive, not breaking. | `uc05/domain/enums.py::IntentKind` |
| A-INTENT-PRECEDENCE | Intent | **INVENTED.** Precedence: frustration → request → decline → confirm → conclusion → casual → off-topic → substantive. | Messages can match more than one set. | A different order changes which of two co-occurring intents wins. | `intent_rules.py::classify_message` |
| A-INTENT-RESULT | Port shape | **INVENTED.** `IntentResult{kind, matched_phrase, rule}`. `matched_phrase` is drawn from **our** vocabulary, never learner free text, so it is safe to log. | Needed for inspectable classification. Deliberately carries **no confidence score**: UC-05's contract has no notion of one. | If the company wants confidence to affect behaviour, that is a contract change, not an adapter change. | `uc05/domain/models.py::IntentResult` |

## 3. Loop protection and generator output

| ID | Area | Assumption | Why | Risk if wrong | Where in code |
|---|---|---|---|---|---|
| A-LOOP-METHOD | Loop detection | **INVENTED.** Comparison is on a normalised token set: lower-case, strip accents and punctuation, drop question-frame stopwords, crude suffix-stem, compare as a set (Jaccard). No model, no embeddings, no data files. | Raw equality misses a reworded repeat; an embedding model would make the rule untestable without a network and non-deterministic. | A rewording that changes the content words defeats it; a different question that reuses the same content words falsely trips it. Both are visible in the recorded `loop_matched_exchange`. | `uc05/domain/normalisation.py` |
| A-LOOP-THRESHOLD | Loop detection | **INVENTED.** Jaccard ≥ **0.80**. Configurable via `LOOP_SIMILARITY_THRESHOLD`. | Measured against the question bank: genuine rewordings score 0.80–0.86, questions that advance score ≤ 0.43. `tests/test_loop_protection.py` asserts both margins so the number cannot silently rot. | Too low → dialogues capped early for no reason. Too high → a paraphrasing generator loops until the cap, which is a worse learner experience but not a correctness failure. | `normalisation.py::LOOP_SIMILARITY_THRESHOLD` |
| A-GQ-RESULT | Port shape | **INVENTED.** `GuidingQuestionResult{question, probing_focus, prompt_version}`. | `probing_focus` is what makes the cap's reasoning chain *assemblable from the record* rather than regenerated. Without it, section 5.6 cannot be honoured honestly. | A real generator that cannot state what it was probing forces `probing_focus` to a placeholder, and the reasoning chain becomes thinner. **Check before integrating.** | `uc05/domain/models.py::GuidingQuestionResult` |
| A-GQ-GUARD | Output guard | **INVENTED.** A guiding question must contain "?", must not contain an answer-disclosure marker, must not contain a praise term, must not restate the learner's question, and must carry a non-empty probing focus. Failing any of these is `ProviderInvalidResponse`. | The brief requires a generator returning a direct answer to be rejected, and requires the check to be mechanical. | A declarative "answer" phrased as a question with no listed marker could pass. The interrogative check alone catches the common case. | `uc05/application/guards.py` |
| A-GQ-DISCLOSURE | Output guard | **INVENTED.** Nine answer-disclosure markers. | Catches an answer wearing a question mark. | Incomplete by nature. | `guards.py::ANSWER_DISCLOSURE_MARKERS` |
| A-GQ-RESTATEMENT | Output guard | **INVENTED.** Similarity ≥ **0.85** to the learner's own question counts as restating. Higher than the loop threshold because a first guiding question necessarily shares subject matter with the question asked. | Section 5.2: the question must move the learner toward the answer "rather than restating the question". | Too low → legitimate first questions rejected. Too high → restatements pass. | `guards.py::RESTATEMENT_THRESHOLD` |
| A-REASONING-CHAIN | Cap output | **INVENTED.** `ReasoningChainStep{exchange_number, guiding_question, probing, learner_response, connection_to_answer}`. | Section 5.6 requires "what each guiding question was probing and how it connected to the answer". | Field names differ from whatever the company expects. Shape is a projection of the dialogue record, so it is cheap to re-shape. | `uc05/domain/models.py::ReasoningChainStep` |
| A-REASONING-TEMPLATE | Cap output | **INVENTED.** `connection_to_answer` is composed from a fixed, position-dependent template around the recorded `probing_focus`. | The chain must reflect what was actually asked, so no generator is consulted. | Reads formulaically. The alternative — regenerating it — would let a generator invent a dialogue that did not happen. | `uc05/application/reasoning_chain.py` |

## 5. Contract gaps we are raising rather than working around

Two places where the published contract does not cover a case UC-05 reaches.
We have **not** widened an enum or bent a domain model to fit; both are noted
here for a contract conversation.

1. **`response_kind` has no "closure" member.** When a learner reasons their
   way to the answer, UC-05 must record *something*. The five permitted values
   are `guiding_question`, `acknowledgement_and_guiding_question`, `exit_offer`,
   `direct_answer` and `capped_answer`. We record
   `acknowledgement_and_guiding_question` and rely on
   `resolution = "learner_reasoned"` to carry the meaning (A-CLOSURE-KIND).
   *Question for the company:* should the vocabulary gain a sixth member, or is
   `resolution` intended to be the discriminator?

2. **The interaction log record is fixed at `mode: "socratic"`.** UC-05 must
   still answer when the mode is off (the brief requires the revert), but has no
   honest way to log that response. We write no record (A-MODE-OFF-LOGGING).
   *Question for the company:* does another component log standard answers, or
   should `mode` become an enum including a non-Socratic value?

## 6. Environment deviation

`structlog` is not available in this environment. Logging is stdlib `logging`
with a JSON formatter, which the brief permits as the alternative. The
allow-list in `logging_config.py` is where the privacy guarantee lives and is
independent of which library emits the line.
